# Automated Wave 4 handoff

This execution packet is subordinate to Petra's accepted decisions, graph
model, runtime contracts, implementation roadmap, frozen UX brief, UX backend
handoff, and UX runtime architecture disposition. It coordinates bounded work;
it does not create new product authority.

## Outcome

Complete Wave 4: working candidates, Review, Brief, and communication.

The authoritative exit gate is:

> One model- or human-produced candidate can appear incrementally in the
> working graph, enter a resumable Review, apply through the authoritative
> path, and update the Brief and History without losing provenance.

## Starting boundary

- Wave 3 is closed. Exact SuggestedAction invocation, bounded Work,
  interruption retention, result delivery, canonical Work History, recovery,
  and post-restart InteractionRun replay are live through the frozen interface.
- ProjectDefinition, Objective, ProjectThread, WorkUnit, InteractionRun,
  Artifact, ContextPacket, EvidencePacket, GroundedResponse, capability,

  authority already exist and remain canonical.
- The scientific evidence-candidate and EvidenceReviewBatch paths are accepted

- Durable profile-neutral WorkingCandidate and working-relationship revisions,
  their authorized Project view and working-graph overlay, complete shared
  ReviewSession composition and missing commands, ProjectBriefView, and the
  first CommunicationPlan/validation receipt remain open.

## Default implementation order

1. Implement the smallest additive, versioned, Project-scoped WorkingCandidate
   and working-relationship contract slice for one registered profile type.
   Bind exact ProjectDefinition, object or predicate schema, producer, Actor or
   model role, ProjectThread/task, Work or run when applicable, input snapshot,
   basis, provenance, uncertainty or limitation, validation, revision, and
   supersession identity. The records are durable working state and have no
   domain authority.
2. Add canonical persistence, idempotent admission and correction, exact-current
   guards, and an authenticated snapshot-consistent query for that slice. Reuse
   existing Artifact, interaction, Work, capability, and Project authority;
   do not duplicate their ledgers. Unknown profile types, predicates,
   references, validators, or incompatible revisions fail closed.
3. Expose the accepted working state as a bounded working-graph overlay and a
   complete textual peer. Keep current authoritative, working, and historical
   state distinct. Graph layout, focus, disclosure, and navigation history stay
   client-local, and graph renderers never query or mutate authority directly.
4. Compose one durable task-sized ReviewSession over canonical candidates,
   validation, ChangeSets, Approvals, commands, events, and projection state.
   Reuse the scientific evidence-review path first without weakening its source
   semantics. Map Current, Candidate, Origin, Basis, Difference, Consequences,
   and Decision roles, ordinary and exception membership, return context,
   freshness, conflicts, atomic boundaries, and member outcomes.
5. Add only the missing typed Review operations needed by the exit trace:
   correction or material basis revision, defer and reopen, refresh, and
   explicit separation. For member recovery, follow D020's two-stage boundary:
   first compose an authenticated, read-only canonical RecoveryAssessment and
   exact member/ChangeSet manifest; later execution may use only an eligible
   existing typed owner that rechecks authority and current state. The Wave 4
   recovery slice implements the assessment only. Conversational text cannot
   authorize an operation. Direct and model-mediated entry must resolve to the
   same candidate, Review, decision, command, and resulting revisions.
6. Apply commitment-ready changes only through the existing exact ChangeSet,
   Approval, command, event, and projection path. One ChangeSet remains atomic;
   a ReviewSession may contain independently atomic ChangeSets and must retain
   every applied, rejected, failed, and unapplied member without reporting
   partial completion as whole success. D021's first ReviewSession checkpoint
   is manual: the authenticated human's exact Apply action supplies the decision,
   and ReviewPolicy is explicitly not applicable. Delegated or automatic Apply
   remains unavailable until a versioned policy owner exists.
7. Add a read-only, snapshot-bound ProjectBriefView with one registered profile
   payload. It must compose exact current Objective, orientation and basis,
   attention, relevant Work, comparison, recent decision, and SuggestedAction
   references from server authority. Do not create universal health, urgency,
   confidence, truth, quality, maturity, or currentness scores.
8. Add the first ProjectDefinition-resolved CommunicationPlan and language-
   validation receipt around an existing bounded response and one linked
   recommendation or action report. Preserve statement-level communicative
   family, origin, force, references, basis, conditions, limitations, action or
   event links, terminology and validator versions, progressive state, and
   passed/repaired/blocked outcome. Communication records never grant mutation
   authority.
9. Map each accepted slice through the frozen design boundary without
   client-side semantic, authority, eligibility, priority, force, or recovery
   calculation. Complete paired-profile conformance and the cumulative live
   exit proof only after the production workbench path uses runtime authority
   without fixture fallback for the demonstrated path.

Change this order only when repository evidence identifies a concrete
dependency, and record the reason in the ordinary roadmap or implementation
report authority.

## Permanent constraints

- Process exactly one bounded implementation or role-owned review slice per
  worker turn and verify it. Commit and push every repository change. A
  bounded review that finds no safe role-owned change may hand off from the
  unchanged clean and pushed commit; never fabricate a change to satisfy the
  alternation.
- Never let model output, Work completion, conversation, graph selection,
  similarity, validation success, or presentation state become Project
  authority.
- Keep origin, basis, provenance, uncertainty, validation, authorship,
  operational completion, Review decision, command result, projection state,
  and domain authority distinct.
- Never create a second candidate, Review, ChangeSet, Approval, command, event,
  projection, Brief, History, communication, Work, interaction, or recovery
  ledger when an accepted owner can be composed.
- ProjectDefinition and registered profile schemas own object, relationship,
  validator, terminology, reference, and discourse meaning. The shared kernel
  and client must not hard-code scientific semantics or accept arbitrary
  client-defined profile payloads.
- WorkingCandidate creation and correction are additive and non-authoritative.
  Promotion begins the existing Review and authoritative application path.
- Similarity may suggest Review grouping but cannot transfer validation,
  approval, atomicity, or authority between members.
- A Review member is the stable inspection and explanation unit. Its ChangeSet
  is the atomic execution and reversal unit. Never offer an execution for one
  member or represent its effect independently from other members in the same
  ChangeSet.
- A RecoveryAssessment is read-only. It separates Review outcome from effect
  knowledge, inventories preserved state, groups complete member outcomes by
  exact ChangeSet, and reports uncertainty when canonical evidence is
  incomplete. It never executes or invents an action.
- Reuse the existing Project History recovery assessment for its narrow
  compensation eligibility facts. Reference or compose that owner where
  applicable; do not duplicate its rules, grant checks, or History facts.
- A structured human checkpoint authorizes an exact commitment. Ordinary assent
  in conversation never substitutes for that checkpoint.
- The manual checkpoint reuses existing ChangeSet, Approval, and command owners
  and current capability grants. It must not invent a ReviewPolicy identity,
  infer policy eligibility, or ask the author to approve the same exact
  commitment twice.
- Preserve exact Project, Actor, definition, thread, task, run, Work, snapshot,
  candidate, relationship, basis, validation, Review, ChangeSet, Approval,
  command, event, projection, Brief, communication, result, and History
  identities wherever applicable.
- Keep graph navigation, unsent edits, disclosure, layout, comparison selection,
  and other presentation state client-local.
- The current version is single-user, but Actor identity and command
  authorization remain mandatory.
- Use the pinned Node 24 toolchain. Run complete verification and real
  PostgreSQL integration whenever a slice changes PostgreSQL behavior.
- The design worker owns frozen components, CSS, browser routes, presentation
  fixtures, accessibility, responsive behavior, and interaction evidence. The
  backend worker must not change them unless the design handoff explicitly
  requests one bounded integration.
- The design worker must not edit runtime contracts, server, persistence,
  migrations, or backend authority. It proposes those changes through the
  handoff.
- Leave the known untracked design image and PDF untouched.

## Review and completion evidence

- Before handing off, test the slice's exact success path and its material
  stale, mismatched, unauthorized, unsupported-profile, retry, and partial-

- For D020's first recovery slice, prove applied and rejected members cannot be
  retried; pending and unknown effects offer status reconciliation only; stale
  or conflicted members require refresh or revision; and failed/no-effect
  members expose retry only when an existing owning idempotency contract proves
  it safe. Prove a shared ChangeSet cannot be represented or acted on partly.
- Before declaring `wave_complete`, run a critic-style engineering pass for
  implicit authority, lost provenance, presentation-specific behavior,
  duplicate ledgers, silent fixture fallback, misleading aggregate status,
  and unsupported completeness claims. Fix every material finding.
- Apply Felicity review to Wave 4 reports and user-facing language, then apply
  the smallest accurate writing corrections. Claims must identify the live
  evidence and its limits.
- Demonstrate at least two materially different registered ProjectDefinitions
  through the shared candidate and Review kernel before closure. A scientific-
  only adapter may be the first slice but cannot establish profile neutrality
  alone.
- The cumulative proof must use fresh stores, exercise the production
  workbench client/controller and frozen rendering path, retain exact durable
  cardinalities and provenance across restart, and state any remaining browser
  automation boundary precisely.
- Run the applicable `UX1.4-EV01` through `UX1.4-EV06` evidence, including
  direct/model-mediated identity convergence, ordinary and exception Review,
  independent partial outcomes, prohibited implicit approval and attribution,
  complete textual parity, keyboard/focus behavior, text scaling, touch,
  forced colors, reduced motion, and non-color meaning.

meaning, profile semantics, architecture, authority, Review atomicity, the
frozen information hierarchy, or the wave exit gate. Return `blocked` for a
failed verification gate, unavailable required service, branch divergence,

both repositories' required work is committed and pushed, the frozen interface
