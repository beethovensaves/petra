## Result

The production Review collection and detail routes now consume authenticated
`petra.project-review-view@1.0.0` records. They no longer look up same-named
reference candidates or derive Review state in React.

V021 establishes `petra.review-session@1.0.0` as a durable identity distinct
from ChangeSet identity. A ReviewSession can exist before any ChangeSet and
retains:

- one Project and exact ProjectDefinition revision;
- an optional exact Objective revision and human responsible party;
- the Project authority snapshot at which the decision context was composed;
- origin and semantic return context;
- ordered ordinary or exception members; and
- ordered exact candidate bindings named by ProjectDefinition semantic keys.

The current reader composes the already implemented scientific path. For each
member, it verifies one exact source-grounded Claim and its `ASSERTS`
relationship, resolves both semantic keys through the bound ProjectDefinition,
and follows every Claim basis span through this Project's exact ProjectSource
registration. It then joins matching ChangeSets and Approvals, distinguishes
validation from human approval, and reports current or stale Project stream
position under one read-only repeatable-read transaction.

The server validates every outgoing view against the canonical contract. The
workbench maps it into the frozen Review presentation model. Collection counts,
candidate comparison, origin, basis, validation, consequences, and an available
ChangeSet preview now come from authority records. A ReviewSession with no
ChangeSet remains inspectable and says that commitment has not been prepared.

## Generality boundary

ReviewSession identity and shared decision context are profile-neutral. The
V021 binding resolver and `project-review-view@1.0.0` renderer are explicitly
the first scientific specialization: one Claim plus one `ASSERTS` relationship
per member. A writing, code, dataset, or other Project may add its own typed
candidate resolver and view payload without changing the shared session
identity or making Projects belong to a template catalogue.

The frozen M1 detail surface can present one member and one current ChangeSet.
The backend contract retains arrays for independent members and ChangeSets; the
client fails explicitly instead of hiding or merging a shape it cannot yet
present. Similarity-based batch suggestions, batch presentation, dependency
grouping, and per-member recovery remain later `UX-REQ-012` work.

## Authority and failure behavior

- A ReviewSession is not an Approval, ChangeSet, command, event, or graph
  projection and cannot alter domain authority by itself.
- Exact retries return the same revision. Rebound identities, skipped revisions,
  changed canonical content, and direct SQL mutation fail.
- Unregistered semantic keys, substituted ProjectDefinitions, unresolved exact
  candidate revisions, invalid Claim–`ASSERTS` pairs, or source basis outside
  the Project fail before commit.
- Another Project cannot read the session. The server returns
  `PROJECT_REVIEW_NOT_FOUND` rather than substituting a global or fixture record.
- A newer event in another Project does not stale this Review. A newer event in
  the same Project marks a pending session stale and blocks decision until a
  fresh comparison and ChangeSet are prepared.
- An excluded ProjectSource, a conflicted ChangeSet, or a failed applicable
  validator is blocking. Warnings require judgment. Passing validators are
  reported as checks only; they do not approve a candidate or establish truth.
- Apply, Reject, and Decide later remain visibly unavailable because this slice
  adds authorized reads, not new browser-owned mutation paths.

## Frozen-design treatment

No design-system CSS, route names, layout, or visual hierarchy changed. Fixture
galleries and component tests retain their neutral examples. Production route
loaders now use live Review queries, and the pre-ChangeSet state is expressed
inside the existing commitment-preview region.
