# M1.9 recovery exercise

Status: `M1.9-T12` pass; `M1.9-W02` complete

Date: 2026-09-04

## Outcome

Petra now has a clean, disposable recovery exercise spanning the authoritative
database, stored bytes, and rebuildable graph. The first run:

- applied all 18 migrations to a new PostgreSQL 18.6 database;
- stored a verified PDF fixture and generated JSON parser output as two real
  content-addressed SeaweedFS objects;
- promoted one Claim and Assertion to trusted revision 2;
- created a 731,801-byte logical backup and copied every stored object with its
  media identity and Petra verification metadata;
- restored the database and objects into separate clean services;
- validated the restored Flyway history against the repository;
- recovered the Project, Work, WorkVersion, SourceSpan, Claim, Assertion, and
  ordered graph outbox at their exact IDs, revisions, and canonical hashes; and
- rebuilt a blank Neo4j to the same active `ASSERTS` identity and SourceSpan
  provenance path.

The source and restored services use independent ephemeral storage. The harness
removes its complete Compose project after success or failure and refuses a
successful result if labeled resources remain.

## Failure boundary

The exercise fails on an empty database dump, incomplete object enumeration,
missing or hash-mismatched restored bytes, altered canonical records, changed
outbox identity or order, migration-history drift, or a graph rebuild that
loses the active Assertion or provenance path. Its result names PostgreSQL as
authority and records that Neo4j was rebuilt rather than restored.

## Hosting implication

This is a quiescent M1 backup, not yet a production multi-writer snapshot
protocol. Hosted Petra must add an explicit backup epoch or write barrier so
the PostgreSQL authority snapshot and ArtifactStore object inventory describe
one consistent point. That extension belongs to deployment hardening; the M1
gate proves the underlying records and projection are recoverable when captured
consistently.
