# M1.5 direct evidence review report

Status: pass  
Scope: `M1.5-W07`–`M1.5-W10`  
Date: 2026-09-02

## Outcome

Petra can now present admitted evidence for a scientific decision and resolve a
direct review gesture through the existing typed authority command path. The
review code does not depend on a model, protocol, database adapter, or visual
component. That lets the workbench and later assistant use the same scientific
semantics while preserving independent UX iteration.

The implemented outcomes are:

| Review outcome | Authoritative representation |
| --- | --- |
| Accept | A human Approval binds one exact promotion ChangeSet; Apply creates trusted Claim and `ASSERTS` revisions together. |
| Reject | A human rejection binds the exact proposed promotion; no Apply command or Neo4j outbox intent is created, and the original quarantine proposal remains inspectable. |
| Correct | The original promotion is rejected; a human-authored, source-grounded replacement proposal carries `supersedes_claim_id` and `supersedes_assertion_id`, passes admission independently, and receives its own decision. |
| Failed or stale | The member returns a typed failure. Other review-batch members continue through their own command transactions. |

Promotion records representation quality and provenance acceptance. It does not
record that a Claim is true.

## Review projection

`buildEvidenceReviewBatchView` joins the smallest material required for review:

- proposal and candidate identity plus role;
- independent admission outcome and whether promotion may be offered;
- exact quote, quote hash, surrounding StructuralBlock text, structural path,
  source pages, content layer, and SourceSpan verification;
- immutable Artifact/hash, ParsedDocument, WorkVersion, and source scope;
- Claim text, kind, full scientific scope, source stance, and paired Assertion;
- deterministic or model extraction identity, declared validator results, and
  warnings.

The returned graph is deeply frozen. An admission-blocked proposal remains
visible with its typed reason but receives `proposed_action: blocked`.
Extractor-declared validation is named separately from independent admission so
the interface cannot accidentally present a model's own check as authority.

## Command path

`buildReviewDecisionCommandPlan` constructs the accepted M1 command contracts:

```text
SubmitChangeSet
  → RecordApproval(approved | rejected)
  → ApplyChangeSet (approved only)
```

The ChangeSet contains one Claim operation and its paired Assertion operation,
exact base revisions and before/after authority, affected and downstream IDs,
an R2 impact statement, Project, proposer, origin, and RFC 8785 content hash.
Command IDs, correlation identity, Approval identity, and idempotency keys are
stable derivations of immutable decision inputs. Every envelope still carries
the caller-supplied capability grant and actor context; building a command does
not authorize it.

`executeReviewDecisionPlan` depends only on the storage-neutral command port.
One direct Apply gesture can therefore submit, approve, and apply without asking
the researcher to confirm the same edit twice, while PostgreSQL still records
all three facts.

## Batch and correction proof

The core suite now contains five end-to-end review cases. It proves:

1. one immutable inspector projection exposes source, scope, origin, and
   validation together;
2. an accepted plan promotes the Claim and Assertion atomically;
3. a rejected plan leaves both original quarantine records unchanged and emits
   no graph projection intent;
4. a corrected proposal retains the rejected original, records human-extraction
   origin and supersession IDs, revalidates its exact span, and promotes only
   through its own ChangeSet; and
5. a stale first member does not prevent a second independent batch member from
   applying.

The generated accepted plan also runs through a disposable PostgreSQL 18.6
instance after all eight forward migrations. The repository retains the exact
ChangeSet, writes trusted revision 2 for both records, and appends the event and
outbox transaction. All 43 PostgreSQL integration tests pass.
