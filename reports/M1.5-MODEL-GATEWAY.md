# M1.5 measured extractor ModelGateway report

Status: provider-neutral foundation passes; live deployment activation pending

Scope: `M1.5-W13`–`M1.5-W15`

Date: 2026-09-02

## Outcome

Petra now has one policy-first route for model-assisted scientific extraction.
The route records why each deployment was eligible or excluded, invokes only an
active role-certified deployment, validates its output against exact source
context, and can create only a quarantine proposal. A model call cannot create
a trusted Claim, approve a ChangeSet, or write a Neo4j edge.

This stage proves the provider-neutral boundary with a deterministic adapter.
It does not report the quality of any external model. `M1.5-W13` remains in
progress until a configured non-fixture deployment runs this route and earns an
active extractor certification.

## Four records separate four meanings

| Record | What it establishes | What it does not establish |
| --- | --- | --- |
| `petra.model-extractor-output` | The provider returned the required scientific fields and source selections. | The fields are grounded, correct, admitted, or trusted. |
| `petra.model-role-certification` | One deployment matched a bounded evaluation fixture for the extractor role under named versions and scope. | Future outputs are correct or the deployment is suitable for another role. |
| `petra.model-request` | One logical task passed or failed routing, budget, and terminal validation with an inspectable decision record. | Any physical call succeeded or produced scientific authority. |
| `petra.model-call` | One physical invocation has exact input, observed deployment, raw output, validation, timing, usage, and cost records. | A valid call output is an accepted scientific Claim. |

The contracts are canonical Draft 2020-12 schemas with generated TypeScript
declarations, Ajv runtime validation, Python `Draft202012Validator` parity, and
strict Pydantic smoke consumption. RFC 8785 identities bind request, call, and
certification content.

## Certification before routing

The initial certification fixture has three exact cases:

1. accept a schema-valid Claim proposal whose quote resolves to the authorized
   SourceSpan and immutable text block;
2. identify a malformed structured response; and
3. identify a schema-valid response whose plausible quote is absent from the
   source.

A deployment becomes active for this fixture only when its observed result
matches every expected case. The resulting metrics are observations such as
case counts and missed expected failures. Petra does not convert them into a
universal model score or a probability that a scientific proposition is true.

Certification binds the deployment revision, role profile, input and output
contracts, prompt profile, validators, domain, language, modality, document
class, dataset snapshot, decision, and invalidation conditions. A provider that
reports a different model revision at call time cannot produce a proposal.

## Policy-first execution

The deterministic router evaluates hard constraints before model preference:

- active routing policy and permitted deployment identity;
- deployment health and verified provider policy;
- E0 local-only processing and accepted data classes;
- active extractor certification for the exact prompt, output schema, and
  scientific scope;
- structured-output and context capacity; and
- request limits for expected validated cost and latency.

Among eligible routes, the gateway selects the lowest expected validated cost,
then latency, then stable deployment identity. The request retains both the
eligible set and every exclusion code. Repeating the same logical workflow and
exact inputs returns the recorded execution without another adapter call.

## Output validation and authority boundary

The provider response schema contains proposed scientific content, scope,
attribution, modality, negation, and source selections. It has no fields for
Petra Claim IDs, authority zones, review state, approvals, or graph operations.

After schema validation, Petra independently verifies that each cited
SourceSpan was included in the outbound context, belongs to the immutable parse
bundle, and contains the exact quoted text. Abstract-only material is restricted
to broad descriptive, comparative, or theoretical proposals. Passing output is
converted into a content-bound evidence proposal whose Claim and `ASSERTS`
relation remain `machine_checked` in quarantine. The existing admission and
human-review boundaries still decide whether it can progress.

Malformed output and false grounding retain their exact raw provider payload
and typed failure. Observed deployment drift also blocks proposal creation. If
a completed call exceeds its token, latency, or monetary budget, the call
remains recorded as a physical success but the logical request ends
`budget_exhausted` and emits no proposal.

## Durable reproducibility record

`V010__model_execution_records.sql` adds append-only tables for role
certifications, logical requests, physical calls, and model evidence proposals.
One transaction stores a request, its ordered calls, and its optional proposal.
Cross-record validation binds the Project, request, call, proposal ID, attempt
order, terminal result, content hashes, and model-extraction provenance before
the transaction begins. PostgreSQL constraints mirror query-critical identity,
routing, egress, outcome, timing, token, cost, and status fields while retaining
the complete contract payload.

The disposable PostgreSQL 18.6 run applies all ten migrations and passes 47
repository tests. It proves exact idempotent replay, cross-record rollback, typed
queries, and database rejection of updates and deletes.
