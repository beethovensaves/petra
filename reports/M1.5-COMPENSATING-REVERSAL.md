# M1.5 compensating scientific-authority reversal report

Status: pass  
Scope: `M1.5-W11`–`M1.5-W12`  
Date: 2026-09-02

## Outcome

Petra can now reverse an accepted Claim–`ASSERTS` pair without deleting the
proposal, human Approval, trusted revision, event, or graph-projection history.
The reversal uses the same content-bound ChangeSet and command path as
promotion. It creates new rejected revisions and changes only the active graph
projection.

A reversal means that the accepted representation is no longer part of active
scientific authority. It does not mean that Petra proved the proposition false,
and it does not alter the source text from which the representation was made.

## Authority semantics

The additive 1.1 contracts introduce two operations:

| Operation | Before | After |
| --- | --- | --- |
| `retract_claim` | trusted, human accepted | quarantine, human rejected |
| `retract_assertion` | trusted, human accepted | quarantine, human rejected |

One reversal ChangeSet must contain exactly one of each operation, use risk
tier R2, name the promotion through `compensates_change_set_id`, and target the
exact revisions created by that promotion. A human Approval still binds the
ChangeSet revision and canonical content hash before application.

The 1.0 promotion records remain valid and replayable. New 1.1 ChangeSet,
command, domain-event, and outbox contracts add reversal without changing the
stored meaning of earlier records. Accepted fixtures cover the reversal
ChangeSet and its submission envelope; runtime tests validate all generated 1.1
commands, events, and outbox records against the canonical registry.

## Non-destructive persistence

`V009__scientific_authority_reversal.sql` extends the guarded PostgreSQL
authority model. Applying a reversal in one transaction:

1. writes Claim and Assertion revision 3 as `quarantine` and
   `human_rejected`;
2. binds both revisions to the reversal ChangeSet and its human Approval;
3. marks the reversal ChangeSet `applied` and the compensated promotion
   `reverted`;
4. appends `change_set.reverted`; and
5. enqueues Neo4j and interface projection records.

Claim and Assertion revision 2 remain trusted historical records. The original
promotion ChangeSet and Approval remain immutable. PostgreSQL rejects a
reversal that names another reversal, a non-applied ChangeSet, a different
Claim–Assertion pair, stale revisions, or authority not created by the named
promotion.

The disposable PostgreSQL 18.6 integration run applies all nine migrations and
passes 44 repository tests.

## Visible graph behavior

The Neo4j projector treats `change_set.reverted` as an ordered authority event.
It upserts the Claim node at rejected revision 3, retains its source-provenance
structure, and tombstones the active Assertion relationship at revision 3. The
edge identity records the tombstone, while PostgreSQL retains the complete
history.

The real PostgreSQL–Neo4j integration proves this sequence:

```text
promotion → ASSERTS revision 2 visible → reversal → ASSERTS absent
          → checkpoint current         → full rebuild → ASSERTS absent
```

After reversal, the Claim remains inspectable with
`authority_zone: quarantine` and `review_state: human_rejected`. The active
`ASSERTS` edge and its provenance path are absent. Rebuilding Neo4j from the
promotion and reversal outbox records reproduces the same state, and all three
Neo4j integration cases pass.

## Replay and UX boundary

Scientific-authority replay now folds both promotion and reversal events. It
returns the current rejected revisions, records which promotion was reverted,
and independently checks revision continuity, compensation identity, authority
state, and Claim–Assertion endpoints.

The direct-review helper builds the complete compensating command plan from a
trusted pair. A later AG-UI interrupt may ask the researcher to approve that
plan, but protocol input will not bypass the same ChangeSet, Approval,
capability, hash, idempotency, PostgreSQL, or projection checks.
