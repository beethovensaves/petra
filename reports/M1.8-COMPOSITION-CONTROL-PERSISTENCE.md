# M1.8 composition control persistence

Status: pass for `M1.8-EV02`; `M1.8-W01`–`M1.8-W03` complete

Scope: PostgreSQL authority, exact replay, normalized dependencies, and immutability

Date: 2026-09-04

## Outcome

CompositionRequest and CompositionPlan are now durable backend records rather
than process-local preparation. Migration V014 stores each immutable payload
with its canonical record hash and the columns needed to enforce identity at
the database boundary.

The request table pins its Project, graph snapshot, requester, content hash,
and ordered subject references. The plan table pins that exact request hash,
the exact EvidencePacket hash, the same Project and snapshot, its state, and
its compiling service. Planned evidence references are stored separately with
section, move, and evidence positions so a later invalidation or graph
projection can traverse dependencies without parsing prose.

## Transaction and replay behavior

- New requests pass the canonical contract and the composition invariant gate
  before storage. Their Project and requesting Actor must already exist.
- New plans require the durable request and EvidencePacket plus the matching
  in-memory EvidencePacket used for semantic validation. A stale or fabricated
  packet cannot be smuggled into the durable path.
- Exact request and plan redelivery is idempotent. Reusing either ID for
  different content is rejected.
- An exact plan replay after process restart reads the durable record without
  requiring the former in-memory packet registry.
- Missing evidence or any failed plan insert rolls back without leaving a
  partial plan or dependency ledger.
- Database triggers reject update and delete operations on requests, subjects,
  plans, and planned evidence references.

Composition controls remain operational provenance. They neither mutate
scientific authority nor authorize publication.
